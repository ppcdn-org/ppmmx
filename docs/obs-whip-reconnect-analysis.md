# OBS Patched WHIP Reconnect Failure Analysis

## Summary

OBS Studio 32.1.2 patched can publish successfully to MMX through WHIP when both applications start normally. If MMX is restarted while OBS remains in the publishing state, OBS does not complete automatic reconnection.

The MMX server accepts the new WHIP POST and establishes the new WebRTC peer connection. OBS then sends a WHIP DELETE for the newly created resource before media track gathering and publisher registration complete.

The evidence currently points to the OBS patched reconnect state machine cancelling its newly created WHIP session.

## Environment

- OBS: `OBS-Studio/32.1.2-patched`
- MMX: `v1.19.1`
- OS: Windows x86_64
- WHIP endpoint: `http://127.0.0.1:8889/live/demo-stream/whip`
- ICE UDP listener: `127.0.0.1:8189`
- Media: three H264 video tracks and one Opus audio track
- MMX track gathering timeout: 10 seconds

## Reproduction

1. Start MMX Origin:

   ```bat
   mmx.exe conf/origin.local.yml
   ```

2. Start publishing from OBS patched through WHIP.
3. Confirm the stream is registered and Tencent forwarding starts.
4. Keep OBS in its publishing state.
5. Stop MMX gracefully.
6. Restart MMX within several seconds.
7. Observe the OBS automatic reconnect attempt.

## Expected Behavior

After MMX restarts, OBS should:

1. Treat the old WHIP resource as gone.
2. Submit a new SDP offer with WHIP POST.
3. Store the new resource URL returned in the Location header.
4. Complete ICE and DTLS negotiation.
5. Keep the new session active and resume media publication.
6. Delete only stale resources associated with previous connection generations.

## Actual Behavior

The observed sequence is:

1. OBS sends DELETE for the resource created by the previous MMX process.
2. MMX returns HTTP 200 even though the old resource no longer exists.
3. OBS sends a new WHIP POST.
4. MMX creates a new session and returns a new Location resource.
5. The new peer connection reaches the connected state.
6. OBS sends DELETE for the newly allocated resource.
7. MMX closes the new session before it becomes a publisher.

## Log Evidence

The old resource cleanup after restart:

```text
WHIP/WHEP session delete requested ...
secret=c5dc3034-c41d-49ac-9bb1-6b222779a4b0
user-agent="Mozilla/5.0 (OBS-Studio/32.1.2-patched; Windows x86_64; zh-CN)"
WHIP/WHEP session was already absent, accepting DELETE
```

MMX then accepts a new WHIP session and establishes its peer connection:

```text
[session 29e7491c] created by 127.0.0.1:50529
[session 29e7491c] peer connection established,
local candidate: host/udp/127.0.0.1/8189,
remote candidate: prflx/udp/127.0.0.1/59002
```

OBS then deletes the new resource:

```text
WHIP/WHEP session delete requested ...
secret=a51fa419-fe53-432d-b21a-c9bd6d8789c7
user-agent="Mozilla/5.0 (OBS-Studio/32.1.2-patched; Windows x86_64; zh-CN)"
[session 29e7491c] closing session after client DELETE
[session 29e7491c] closed: terminated
```

The new session never reaches:

```text
is publishing to path 'live/demo-stream'
```

## Secret Ownership

The WHIP resource secret is generated by MMX for every new WHIP POST:

```go
s.secret = uuid.New()
```

It is returned to OBS through the Location response header:

```http
Location: /live/demo-stream/whip/<secret>
```

The secret is only a resource identifier. It does not contain or persist:

- SDP state
- ICE credentials or candidates
- DTLS state
- PeerConnection state
- RTP tracks
- Encoder state

Therefore, a resource secret from the previous MMX process cannot reconstruct a WebRTC session after server restart. OBS must create a new WHIP resource and retain the newly returned Location value.

## Server-Side Changes Already Applied

MMX now treats DELETE as idempotent:

- Existing resource: close it and return HTTP 200.
- Missing resource after restart: return HTTP 200.

This avoids blocking reconnect when OBS first cleans up a stale Location.

MMX also binds the local ICE socket explicitly:

```yaml
webrtcLocalUDPAddress: 127.0.0.1:8189
webrtcIPsFromInterfaces: false
webrtcAdditionalHosts: [127.0.0.1]
```

This prevents ICE candidate changes across physical and virtual Windows interfaces after restart.

## Likely OBS Client Defect

The reconnect implementation likely has a stale cleanup action or generation race:

1. Reconnect generation A owns the old WHIP resource.
2. Reconnect generation B creates and stores a new WHIP resource.
3. A delayed cleanup from generation A reads shared mutable resource state.
4. The cleanup deletes generation B's new Location instead of generation A's old Location.

Another possibility is that a timeout from the previous reconnect attempt cancels the current attempt after the new PeerConnection has already connected.

## Recommended OBS Changes

### Connection Generation

Assign a monotonically increasing generation ID to every publish attempt.

Each asynchronous callback must verify that it still belongs to the active generation before it can:

- update the active resource URL
- stop the publisher
- send DELETE
- modify reconnect timers
- report a terminal failure

### Immutable Resource Ownership

Store the WHIP Location returned by each POST on the connection attempt object, not in a single shared mutable string.

Cleanup must delete exactly the Location owned by that attempt:

```text
attempt.oldResourceURL -> DELETE oldResourceURL
attempt.newResourceURL -> DELETE newResourceURL only when that same attempt ends
```

Do not resolve the URL from global publisher state at delayed cleanup time.

### Timer Cancellation

When a new attempt becomes active, cancel all timers associated with previous attempts:

- reconnect timeout
- handshake timeout
- media-start timeout
- delayed cleanup
- retry backoff callback

A timer callback must also check its generation before taking action.

### Reconnect State Transition

After a successful WHIP POST and ICE connection:

```text
RECONNECTING -> NEGOTIATING -> CONNECTED -> PUBLISHING
```

Do not issue DELETE merely because media tracks have not immediately produced packets. Allow the configured startup and encoder warm-up window.

### Stale DELETE Handling

On server restart, deleting the previous Location can return either 200 or 404 under normal WHIP semantics. The client should treat both as successful stale-resource cleanup and continue with a new POST.

MMX currently returns 200 for both cases for OBS compatibility.

### Logging Required in OBS

Add logs containing the connection generation and exact resource URL:

```text
[WHIP generation=12] POST endpoint=...
[WHIP generation=12] created resource=...
[WHIP generation=11] cleanup resource=...
[WHIP generation=12] ICE connected
[WHIP generation=12] publishing media
[WHIP generation=12] DELETE resource=... reason=...
```

The DELETE reason is particularly important. It should identify whether deletion was caused by:

- user stop
- server disconnect
- reconnect replacement
- negotiation timeout
- encoder failure
- stale generation cleanup

## Acceptance Criteria

1. Start MMX and OBS; initial publishing succeeds.
2. Restart MMX while OBS remains publishing.
3. OBS may DELETE the old resource once.
4. OBS creates a new WHIP resource.
5. OBS does not DELETE the new resource from a stale callback.
6. MMX logs the new session as publishing:

   ```text
   is publishing to path 'live/demo-stream'
   ```

7. Tencent forwarding restarts for `_q0`, `_q1`, and `_q2`.
8. Repeat MMX restart at least 20 times without manually stopping and starting OBS.
9. No orphan reconnect timers or duplicate active WHIP resources remain in OBS.

## Additional Validation

Compare the patched OBS behavior against official OBS or another WHIP publisher. If another publisher reconnects successfully under the same MMX restart procedure, it further confirms the defect is in the patched OBS reconnect lifecycle.
