# OBS ↔ origin-mmx 推流降级协商规程

## 目标

推流出现 RTP 丢包时，自动逐步降低 OBS 推流的同播层数/码率，优先保证流畅性而不是画质，避免持续丢包导致画面卡顿/花屏。

## 一、触发条件与状态机

状态按 **path**（如 `live/table1-fwv`）维护，不按 WHIP session ID 维护——因为降级/恢复动作本身是通过让 OBS 重启推流来生效的，重启会产生全新的 session ID，状态必须跨重启存活，否则会跟着每次重启反复抖动、误判。

**满载层数（maxLayers）是动态的，不是写死的 3**。不同 OBS 画质档位协商的真实同播层数不一样（比如 1080P 是 4 层，720P 是 3 层），状态机按该 path **第一次**真实推流会话实际协商到的视频轨道数确定 maxLayers，后续只会向上更新（比如从 3 层的画质档位切到 4 层），不会因为降级触发的重连、重连后真实层数天然低于 maxLayers（这正是降级要达到的效果）而被误判为"容量变小"。

```
maxLayers / 码率100%（初始，满载）
   ↓ 瞬时丢包率>5% 或 5min均值丢包率>1%，持续>60s        ↑ 合规>60s
maxLayers-1 / 码率100%
   ↓ 同上，持续>60s                                       ↑ 合规>60s
   ...（逐层往下，直到 1 层）...
1层 / 码率100%
   ↓ 同上，持续>60s                                       ↑ 合规>60s（先恢复码率）
1层 / 码率80%（终止态）
   ↓ 仍不合规 → 停止自动动作，仅告警                       ↑ 合规>60s → 回到"1层/码率100%"，
                                                              再观察60s合规才继续升层级
```

规则：
- 单向阶梯，一次只走一级，不允许跨级跳变。
- 降级、恢复共用同一套阈值，不设滞回区间（如实测发现阈值边界抖动，再补）。
- 终止态（1层/码率80%仍不合规）不再自动继续降码率，只记日志/告警，交人工处理。
- 每次状态转移后进入 60s 观察期，期间不做新判断。
- maxLayers 未知时（该 path 还没有任何真实推流会话上报过层数）状态机不做任何降级动作。

### 层数减少的方向：从高分辨率层开始砍

**同播层数减少时，砍掉的是当前最高分辨率的那一层，保留分辨率更低的层**（例如 1080P/720P/480P/360P 四层同播，`layers` 从 4 降到 3 时，砍掉的是 1080P 层，保留 720P/480P/360P；继续降到 2 时再砍掉 720P，以此类推）。恢复时按相反顺序，从低到高逐层加回。

这是本协议的**硬性约定**，理由：
- 目标是"优先保证流畅性而不是画质"（见上方「目标」一节）——保留低分辨率/低码率层才能在丢包压力下继续维持画面不卡顿；反过来砍低分辨率层、保留高分辨率层，会让码率负担不降反升，与"降级"的目的矛盾。
- mmx 侧（本仓库，见 [internal/servers/webrtc/degrade.go](../internal/servers/webrtc/degrade.go)）**只维护一个抽象的层数整数**，不感知每一层具体对应的分辨率/码率/RID，也不参与决定重启后具体保留哪几条 simulcast 轨道——`layers` 数字降低到几，由 OBS 侧执行器在收到 `TARGET_STATE` 后自行决定保留哪几层再重启推流。因此"从高分辨率开始砍"是**OBS 侧执行器必须遵守的约定**，不是 mmx 能够检查或强制的行为；mmx 只保证数字本身单调、每次只变化一级。

## 二、mmx 任务

1. **丢包率计算**：每个 WHIP（publish）session，每 1s 采样 `InboundRTPPackets`/`InboundRTPPacketsLost`（已有字段，见 [internal/servers/webrtc/session.go](../internal/servers/webrtc/session.go)）差分算出瞬时丢包率，维护 5 分钟滑动窗口算出均值丢包率。
2. **状态机**：按 path 维护 `{当前层级, 当前码率比例, 上次动作时间}`，跑上述状态机；WHIP session 重连后先查该 path 是否已有状态，有则延用，不重置。
3. **新增 WS 端点**，路径与对应 WHIP 推流地址绑定（如 `ws://.../live/table1-fwv/ws/whip`，从 WHIP 推流地址 `.../live/table1-fwv/whip` 去掉 `/whip`、换成 `/ws/whip`，这也是 OBS 侧实测已经在用的推导方式）：
   - **鉴权**：固定共享密钥，不是签名/带过期时间的 token（那套复杂度是给外部公开 API 防重放用的，这个 WS 端点从头到尾只有 OBS 侧这一个可信客户端，不需要）。密钥就是 mmx 部署环境变量 `WHIP_WS_SECRET` 的值，两种方式任选一种带上：
     - Header：`Authorization: Bearer <secret>`
     - 或查询参数：`ws://.../live/table1-fwv/ws/whip?token=<secret>`
     - 两个都没带 / 值不对，返回 `401`，mmx 会记一条 `WAR [degrade] path=... executor connection rejected` 日志（不会记密钥本身）。
   - **声明式推送协议**（每次都发"当前应处于的目标状态"，不是一次性指令，避免消息丢失导致两端状态不一致）：
     ```json
     {"type":"TARGET_STATE","path":"live/table1-fwv","layers":2,"bitrate_percent":100}
     ```
     - WS 连接建立时立即发一次当前状态（前提：mmx 已经从至少一次真实推流里学到过 `maxLayers`，否则不发，见上一节）。
     - 状态机每次转移时再推送一次。
   - 终止态额外推一条纯提示，不代表要执行任何动作：
     ```json
     {"type":"ALERT","path":"live/table1-fwv","reason":"layer=1,bitrate=80%,仍不合规"}
     ```

## 三、OBS 侧任务（需求定义，不限定实现方式）

需要一个跟 OBS 同机/同网运行的组件，具体如何与定制版 OBS 通信，由 OBS 侧自行决定。目前 OBS 补丁里已经直接内置了 WS 客户端（不是独立进程），对外契约如下：

- **连接**：WHIP 推流地址 `.../{path}/whip` 对应的 WS 地址是 `.../{path}/ws/whip`（同 host:port，`ws://` 而非 `wss://`，除非 mmx 开了 TLS）。
- **鉴权**：按上一节的方式带上 `WHIP_WS_SECRET`（Header 或 query 二选一）。这个密钥目前只存在于 mmx 部署环境的 `bin/.env` / VPS 上的 `.env`，需要单独同步给 OBS 侧配置，不在这份文档里明文写出。
- **输入**：监听 `TARGET_STATE` 消息。
- **行为**：收到 `TARGET_STATE` 时，确保 OBS 当前实际的同播层数、码率与消息里的 `layers`/`bitrate_percent` 一致，不一致则通过重启推流的方式切换到目标状态。**层数减少时必须砍掉当前最高分辨率的一层**（见第一节「层数减少的方向」），层数增加时按相反顺序、从低到高逐层加回；不得跨级跳变、不得砍非最高层。
- **幂等性要求**：收到的 `TARGET_STATE` 如果与 OBS 当前状态已经一致，不应重复触发重启（避免连接建立时收到的初始状态消息造成无意义重启）。
- **无需回报**：单向声明式协议，不需要向 mmx 汇报执行结果或本地状态。

## 四、已知的、接受不处理的副作用

降级/恢复触发的推流重启，可能被现有 `record: yes` 自动录像逻辑当作"流下线又上线"，从而切出新的录像分段，把一局录像物理上拆成两段。**这个副作用已确认，决定不做特殊处理**，不在本协议范围内解决。

## 五、后续实现顺序

1. mmx 侧丢包率计算 + 状态机 + WS 端点
2. OBS 侧对接：连接 WS、解析 `TARGET_STATE`、按目标层级/码率重启推流
3. 联调，验证完整降级/恢复流程
